Loads a packet's actual content. The catalog in your system prompt is an index: it tells you WHICH packet to load and is never itself an answer, so a question the catalog appears to describe is a question you must load a packet to answer. That said, MOST TURNS NEED NO CALL: it acquires knowledge you do not have; it is not an acknowledgement of a turn, not a refresh, and not a way to confirm what is loaded. Before calling, check in order: (1) can you answer from the CONTENT of packets already loaded? Then answer — do not call. (2) Is the material inside a packet already in this conversation? Then re-read it — do not call; a loaded packet never needs re-requesting. (3) If the catalog names a row that covers the gap AND that row is absent from your active set, call with exactly those ids -- and do NOT reply until it returns. That third test decides both things: while it is true you must load and must not answer; once it is false you must answer and must not call. Requesting ids that are already active is an error: it loads nothing, costs a round trip, and disturbs eviction order.

ONE ROUND TRIP, EVERY ID. The limit is on round trips, not on packets: one call carries as many ids as you need. When you do call, carry your whole retrieval need in it. Work out that need before you call: re-read the question end to end, and name an id for EVERY part of it. Multi-part questions are the common trap — a question that asks about a form and a fee, or a rule and the procedure that follows it, usually needs a packet for each part, and they often sit in different branches. Include ids you are only fairly sure about: one extra packet costs a fraction of what a second call costs, because a second call is a whole model round-trip the user sits and waits through. Sibling calls issued together in one message are merged into a single load anyway; a call issued after seeing the first result is the expensive one. If you find yourself about to make a follow-up load because you were unsure, the first call should have been wider. But if the content you loaded turns out not to hold the rule, call again with the id that does -- answering from content you can see is insufficient is the worse outcome by far.

Request the deepest matching ids straight from the catalog — you never need to load a parent folder on the way to a child, and one call can carry ids from several branches. Pass the ids you need in `requested_packet_ids` and the ids you believe are currently active in `active_packet_ids`. Returns delta (loaded + evicted).
